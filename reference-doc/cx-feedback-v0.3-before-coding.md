# CX Feedback — v0.3 Before Coding / v0.3 编码前反馈

**English (primary):** The v0.3 plan and HLD are materially stronger than the prior design and should retain their core safety posture: M0 remains read-only with no executor or validator write path; M0A is a hard containment gate before M0B; the worker is untrusted and capability-limited; policy bundles are immutable and per-episode bound; only the verifier can resolve an episode; telemetry loss is an incident; and missing data must never imply validator health. However, this is a conditional no-go for implementation until the delivery definition is completed. M0 must be stated as a single-Agave-validator, testnet-only, read-only incident-analysis assistant for a named on-call operator—not an autonomous validator operator—and must have a frozen product hypothesis, supported fault classes, watchtower baseline, report/alert workflow, human feedback rubric, and measurable targets for diagnosis quality, recommendation actionability, report latency, operator burden, cost, and observation impact. Resolve and assign owners, approvers, due dates, defaults, and evidence for the M0A blockers: implementation language and pinned SDK/model (D1/D7), testnet environment (D3), alert channel (D5), initial safe limits and trial/pass rules (D6), sandbox backend (D11), bundle-signing key custody (D14), external audit-anchor service/cadence/maximum lag (D15), and single-host UDS capability transport (D16). Keep D13 multi-validator shadowing, D10 offline tuning, D17 public metrics, non-Agave clients, and M1 execution out of M0. Correct the cross-document issues before coding: D3 is called both an M0 and Phase-4 decision; consensus determination is described as both three-way and four-input; the HLD exit criterion requires a “correctly ranked hypothesis” although the schema has no ranking field; and W1 cannot validate a configuration until its language, SDK version, and model are pinned. Add a time-boxed M0A charter, DRIs, estimates, critical path, environment-readiness checklist, change-control process, data retention/access policy, backup/recovery tests, degraded-mode runbooks, and explicit go/no-go authority. Split D6 into an auditable parameter register with units, owner, safe initial value, bounds, measurement source, and review cadence; set deterministic security gates to 100% pass and evaluate model-quality gates with frozen fixtures, repeatable controls, confidence reporting, and human adjudication. Permit M0A coding only after this package is approved, and permit M0B only after M0A demonstrates real—not mocked—transport boundaries, fail-closed sandboxing, external audit anchoring, and validated SDK behavior; advance to M1 only when both safety gates and operator-value evidence pass.

**中文（次要翻译）：** v0.3 计划和 HLD 相比上一版在安全性与可运维性方面有实质提升，应保留其核心安全边界：M0 必须保持只读，不得存在执行器或任何验证节点写入路径；M0A 必须作为 M0B 之前不可绕过的隔离门槛；Worker 应被视为不可信且只能持有受限能力；策略包必须不可变并与单个事件绑定；只有 Verifier 可以将事件置为已解决；遥测丢失本身必须成为事件；缺失数据绝不能被视为验证节点健康。但在补齐交付定义前，不建议开始实现，当前结论为“有条件不启动”。应明确 M0 是服务于指定值班人员的、仅支持一台 Agave 测试网验证节点的只读事故分析助手，而不是自主验证节点运维系统；并在 M0B 前冻结产品假设、支持的故障类别、watchtower 基线、报告/告警流程、人工反馈量表，以及诊断质量、建议可执行性、报告时效、值班负担、成本和观测影响的量化目标。应为 M0A 阻塞项指定决策人、审批人、截止日期、逾期默认方案和所需证据：实现语言及固定 SDK/模型版本（D1/D7）、测试网环境（D3）、告警渠道（D5）、初始安全阈值及试验/通过规则（D6）、沙箱后端（D11）、策略包签名密钥保管（D14）、外部审计锚定服务/频率/最大延迟（D15），以及单主机 UDS 能力传输方案（D16）。D13 多验证节点影子运行、D10 离线调优、D17 公开信任指标、非 Agave 客户端和 M1 执行能力均不应进入 M0。编码前还应修正跨文档矛盾：D3 同时被定义为 M0 和 Phase 4 决策；共识模式判定同时被写成三方和四输入；HLD 要求“正确排序的假设”，但数据模型没有排序字段；以及在语言、SDK 版本和模型尚未固定前，W1 无法验证具体配置。还应补充有时限的 M0A 章程、责任人、工期估算、关键路径、环境就绪清单、变更控制、数据保留与访问策略、备份恢复测试、降级运行手册和明确的 go/no-go 授权机制。D6 应拆分为可审计的参数登记表，包含单位、责任人、安全初值、上下限、测量来源和复审周期；确定性安全测试应要求 100% 通过，而模型质量测试应采用冻结样本、可重复控制、置信度报告和人工裁决。只有在上述材料获批后才可开始 M0A 编码；只有在 M0A 用真实而非模拟的能力边界、失效即关闭的沙箱、外部审计锚定和已验证的 SDK 行为通过验收后，才可开始 M0B；只有安全门槛和操作人员价值证据均达标后，才可进入 M1。
